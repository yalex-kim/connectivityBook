Chapter 13

Classic 보안: 레거시 PIN에서 Secure Connections까지

BR/EDR 보안은 세 번 바뀌었다. 처음에는 PIN과 SAFER+ 블록 암호로 키를 만들고 E0 스트림 암호로 암호화했다. 2.1의 Secure Simple Pairing(SSP)은 타원곡선 Diffie-Hellman과 HMAC-SHA-256으로 키 합의를 바꿨다. 4.1의 Secure Connections는 곡선을 P-256으로 올리고 장치 인증과 암호화를 AES로 바꿨다. 이 장은 세 세대의 함수를 모두 구현해 Part G의 예제 데이터와 맞춘다. 공격 절차가 아니라 각 방식이 무엇을 지키고 왜 바뀌었는지가 목표다.

  • 레거시·SSP·Secure Connections가 각각 어떤 키 합의·인증·암호화를 쓰는지 표로 구분할 수 있다.
  • SAFER+ 기반 E22·E21·E1·E3의 입력과 출력(K_init, 결합 키, SRES·ACO, K_enc)을 설명할 수 있다.
  • SSP의 f1(약속)·g(숫자 비교)·f2(링크 키)·f3(확인)과 IOcap 인코딩을 따라갈 수 있다.
  • Secure Connections의 h4·h5·h3과 BR/EDR AES-CCM의 nonce·B1 형식을 적용할 수 있다.

바뀐 이유는 한 줄로 말할 수 있다. 레거시는 비밀이 PIN뿐이라 짧은 PIN이면 엿들은 교환으로 PIN을 추측해 볼 수 있었다. SSP는 비밀을 ECDH로 만들어 엿듣는 것만으로는 키를 얻을 수 없게 했고, 사람이 숫자를 비교하거나 패스키를 넣어 중간자를 막는다. Secure Connections는 곡선과 대칭 암호를 현대 표준으로 맞췄다. 그래서 GAP의 Secure Connections Only 모드는 BR/EDR의 서비스에 보안 모드 4 레벨 4(인증된 P-256 링크 키와 AES-CCM)를 요구한다.

열쇠 맞추기

레거시는 둘이 미리 정한 짧은 암호(PIN)를 섞어 열쇠를 깎는 것이다. 암호가 짧으면 엿들은 사람이 하나씩 대 보며 같은 열쇠를 깎아 볼 수 있다. SSP는 각자 비밀을 하나씩 갖고 공개된 재료만 주고받아 같은 열쇠를 만드는 방식(ECDH)이라, 엿들어도 열쇠를 못 깎는다. 다만 중간에서 둘 다인 척하는 사람을 막으려고 마지막에 화면의 여섯 자리 숫자를 서로 비교한다.

레거시: SAFER+로 만든 E 함수들

레거시의 모든 키 함수는 128비트 블록 암호 Ar(= SAFER+)와 그 변형 A′r(1라운드 입력을 3라운드 입력에 다시 더해 역함수를 없앤 것)로 만든다. 한 라운드는 바이트마다 라운드 키를 XOR 또는 더하기 → e(45i mod 257) 또는 그 역 l → 다음 라운드 키를 더하기 또는 XOR → 2바이트 PHT(a, b → 2a+b, a+b) 4층과 그 사이 “아르메니아 셔플” 3번이다. 8라운드 뒤 17번째 키를 더한다. 라운드 키는 17바이트 레지스터를 매번 3비트 돌리고 바이어스 Bp[i] = 454517p+i+1를 더해 만든다.

  • E22(K_init, 임시 키): PIN′ = PIN 뒤에 BD_ADDR을 붙여 최대 16바이트로, A′r(PIN′ 반복, RAND ⊕ L′·2120).
  • E21(결합 키 재료): A′r(RAND ⊕ 6·2120, 주소 반복).
  • E1(장치 인증): Hash(K, RAND, 주소, 6) = A′r(K̃, E(주소) +₁₆ (Ar(K, RAND) ⊕ RAND)). 앞 4바이트가 SRES(응답), 나머지 12바이트가 ACO.
  • E3(암호화 키): Hash(K, EN_RAND, COF, 12) → K_enc. 그 뒤 협상한 키 길이로 줄여 E0에 넣는다.

Secure Simple Pairing: ECDH와 f1·g·f2·f3

SSP는 다섯 단계다. ① 공개 키 교환(PKa, PKb) ② 인증 1단계: 숫자 비교·Just Works·패스키·OOB 중 하나 ③ 인증 2단계: 확인 값 Ea·Eb 교환 ④ 링크 키 계산 ⑤ LMP 인증과 암호화. 함수는 모두 SHA-256 기반이다.

Secure Connections: h4·h5·h3과 AES-CCM

P-256으로 링크 키를 만든 뒤 장치 인증은 E1 대신 h4(장치 인증 키 = HMACLK("btdk" ‖ A1 ‖ A2)) → h5(HMACS(AU_RAND_C ‖ AU_RAND_P))를 쓴다. h5 출력의 앞 32비트가 SRES_C, 다음 32비트가 SRES_P, 나머지 64비트가 ACO다. 암호화 키는 h3 = HMACLK("btak" ‖ A1 ‖ A2 ‖ ACO)의 앞 128비트다.

암호화는 AES-CCM(M = 4, L = 2)인데 B1이 표준과 다르다. 연관 데이터 길이를 넣지 않고 바로 패킷 헤더 2바이트(ARQN·SEQN·FLOW를 0으로 가림)와 페이로드 헤더 1바이트(FLOW를 가림)를 넣는다. nonce 13바이트는 ACL이면 PayloadCounter 형식(39비트 카운터 + 길이 0 이어짐 비트 + 방향 비트 + IV), eSCO면 클록 형식(CLK₂₇₋₁ + dayCounter + IV)이다. IV는 암호화 시작 때 마지막 h5의 ACO, 재개 뒤에는 EN_RAND다. eSCO는 MIC 없이 암호화만 한다.

키 길이를 줄이기로 협상했으면 키의 하위 바이트를 0으로 바꾼다. 협상 범위는 7~16바이트이고, 호스트는 HCI로 받아들일 최소 길이를 정할 수 있다. 짧은 키는 그만큼 추측 공간이 작으므로 16바이트를 요구하는 것이 안전한 설정이다.

핵심 정리

  1. 레거시: SAFER+(Ar, A′r)로 E22(K_init), E21, E1(SRES·ACO), E3(K_enc), 암호화는 E0. 비밀은 PIN뿐.
  2. SSP: ECDH(P-192) + HMAC-SHA-256의 f1(약속)·g(여섯 자리)·f2(링크 키)·f3(IOcap을 묶은 확인).
  3. Secure Connections: P-256, h4 → h5(SRES_C·SRES_P·ACO) → h3(AES 키), AES-CCM의 B1은 길이 없이 헤더만.
  4. nonce: ACL은 PayloadCounter + 방향 비트, eSCO는 CLK + dayCounter. IV는 ACO 또는 EN_RAND.
  5. 안전한 설정: Secure Connections Only(보안 모드 4 레벨 4), 키 길이 16바이트.

확인 퀴즈

E1 출력 중 ACO는 어디에 쓰이나?

§6.1: ACO는 E3에 쓰는 Authenticated Ciphering Offset. Secure Connections에서는 h5의 ACO가 h3과 nonce의 IV에 쓰인다.

PIN이 4바이트일 때 E22의 L′은?

L′ = min(16, L + 6) = 10. PIN 4바이트 뒤에 BD_ADDR 6바이트가 붙는다.

f3에 IOcap을 넣는 이유는?

IO 능력으로 인증 방식이 정해지므로, 이를 바꿔 약한 방식으로 떨어뜨리는 시도를 확인 단계에서 잡는다.

BR/EDR AES-CCM의 B1이 표준 CCM과 다른 점은?

§9: RFC 3610에서 B1의 AAD 길이를 빼는 수정. B1 = 패킷 헤더 2 + 페이로드 헤더 1 + 0 13개.
